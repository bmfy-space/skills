# Developemnt Plan

用于在写代码前完成需求澄清、计划制定和待办维护。不要自动切换到 Claude Code 内置 plan mode，本技能以文件化 `plan.md` / `todo.md` 为准。

## 适用场景

当任务涉及产品、功能、接口、页面、非平凡 bug、重构、测试、构建、自动化、第三方接入，或存在多步骤、多文件、需求取舍时使用。

明显的小改动可跳过；只要需求、边界、方案或验收标准不清晰，就必须使用。

## 硬性流程

在写代码、改文件、安装依赖、运行迁移或生成脚手架前，必须完成：

1. 探索与任务直接相关的项目上下文。
2. 检查 `.developemnt-plan/` 中是否已有相同或相似主题。
3. 向用户提出足够详细的澄清问题；不限制问题数量，复杂任务持续追问到需求清晰。
4. 确认目标、边界、优先级、非目标和验收标准。
5. 创建或更新同一主题下的 `plan.md` 和 `todo.md`，不要创建其他额外文件。
6. 向用户展示计划摘要，然后按 `todo.md` 执行；只有仍有阻塞、破坏性操作或未确认边界时才再次询问。

## 澄清要求

澄清阶段要主动发散，不只按用户字面需求推进。优先确认：

- 要解决的问题、目标用户和使用场景。
- 成功标准、验收方式和优先级。
- 范围边界、非目标和时间限制。
- UI、交互、性能、安全、兼容性等约束。
- 技术方案偏好、禁忌、风险和替代方案。

每个问题尽量给出可选方案和推荐项；选项数量不设固定上下限，以覆盖真实选择空间为准，可包含“其他 / 自定义输入”。不要只抛开放式问题。

## 文件位置

必须写入当前项目根目录下的 `.developemnt-plan/`，且主题文件夹必须严格命名为 `YYYYMMDDHHmmss-<topic>`：

```text
.developemnt-plan/YYYYMMDDHHmmss-<topic>/plan.md
.developemnt-plan/YYYYMMDDHHmmss-<topic>/todo.md
```

`YYYYMMDDHHmmss` 使用创建或更新该计划时的时间；`<topic>` 使用短横线命名。目录名按用户指定拼写为 `developemnt-plan`，不得改成其他名称或格式。

如已有相同或相似主题，更新既有文件夹中的 `plan.md` 和 `todo.md`，不要重复创建。

## `plan.md` 内容

必须简洁可执行，包含：

```markdown
# <任务名称> 实现计划

## 背景
- <问题和相关上下文>

## 目标
- <本次交付内容和完成判断>

## 非目标
- <本次明确不做什么>

## 约束与假设
- <限制、风险、仍需确认的信息>

## 方案
- <推荐方案、关键权衡、排除的备选方案>

## 实施步骤
1. <具体步骤>

## 验证方式
- <静态检查 / 测试 / 手动验证>

## 风险与回滚
- <主要风险和恢复方式>
```

## `todo.md` 内容

必须是可持续更新的 checklist。可使用平级结构，也可使用两级结构：第一级对应大模块，第二级对应大模块中的小模块。

```markdown
# <任务名称> Todo

## 状态说明
- `[ ]` 未开始
- `[~]` 进行中
- `[x]` 已完成
- `[!]` 阻塞或需要用户确认

## 待办

### 平级模式
- [ ] 1. 探索项目上下文
- [ ] 2. 澄清需求并确认边界
- [ ] 3. 制定实现计划
- [ ] 4. <实施步骤>
- [ ] 5. 验证并汇总结果

### 分级模式
- [ ] 1. <大模块一>
  - [ ] 1.1 <小模块一>
  - [ ] 1.2 <小模块二>
- [ ] 2. <大模块二>
  - [ ] 2.1 <小模块一>
  - [ ] 2.2 <小模块二>
```

执行时必须在开始、完成、阻塞或计划变化时同步更新 `todo.md`；计划变化时同步更新 `plan.md`。

## 范围控制

如果需求过大，先拆成可独立交付的子任务，说明推荐优先做哪部分和原因，等待用户确认后再继续计划该子任务。

不要添加用户未要求、计划未覆盖的功能。

## 完成标准

只有同时满足以下条件，才能说任务完成：

- `plan.md` 和 `todo.md` 已落盘且反映最终状态。
- 所有完成项已在 `todo.md` 更新。
- 代码或配置变更与计划一致。
- 验证方式已执行，或明确说明为何无法执行。
- 未完成、跳过或失败事项已清楚记录。
